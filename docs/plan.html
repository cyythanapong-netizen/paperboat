The shape

Three pages, one app

Every app built on Paperboat has the same three pages, plus a Console for logs. A domain only defines the things that live on each page; the pages themselves are generic.

1 · Station

Scene of things and connections

2D or 3D. Entities have a position, typed settings, and ports. Connections here are physical: a member between two joints, a motor on a cart, an inlet on a wall.

→
2 · Flow

Blocks and wires

Grasshopper / DaVinci style. Sources and probes from the station show up as blocks. You drive sources with functions, route probes to monitors, and fan lists out into sweeps.

→
3 · Dashboard

Instruments

Built from the monitor blocks in the flow (scopes, lamps, readouts), plus per-block progress, cancel and re-run. Logs go to the Console. Only changed blocks re-run.

Design rule

Station says where, Flow says what

The physics stays in the station and the solver (the plant). The flow never contains plant blocks, which is what separates it from Simulink, where you build the plant out of blocks. Two kinds of block are anchored in the station:

  • Sources push on the scene: a force source on a joint, a motor on a cart, an inlet on a channel. Each appears in the flow as a block with an input that you drive with a function (step, ramp, sine, expression, CSV).
  • Probes are places you choose to measure: displacement at a joint, stress in a member, the angle of a link, pressure at a point. Each appears in the flow as a block with outputs.

Wires come in three kinds, each with its own look, and ports only accept the matching kind:

WireCarriesExample
Signal · thickA time series on the run clock, with a unitForce in kN, displacement in mm, angle in rad
Value · thinA number, flag or setting, fixed for one runThreshold 10 mm, LQR weight Q, trip flag
Result · dashedA finished object, computed once and cachedMesh, gain matrix, mode shapes, sweep table
Monitoring

Monitor blocks build the Dashboard

Each monitor block in the flow becomes one instrument on the Dashboard. You lay the instruments out once and the layout is saved with the project, so the Dashboard needs no separate UI work.

  • Scope (the graph; goal: the "mother of all scopes", with zoom, cursors, triggers, X–Y and export) takes any number of signals and overlays them. Diff mode plots A − B when the units match, and A against B on two axes when they don't.
  • Lamp takes a threshold and a comparison and lights in the signal colour (a warning) or red (a trip), saying its state in words. It can latch when tripped, and its output y can stop the run.
  • Readout shows the current value, the peak and the RMS.
  • Taps: drag any port or wire onto a graph to add that signal. Dragging a block's input and its output onto the same graph gives a before/after comparison, such as commanded force against reaction force, or a filter's input against its output.
Execution

How a Signal flow runs

A Signal flow (causal): wires carry values one way, the graph is sorted once, and feedback closes through the plant (a probe reads the state the previous step left). Two run modes:

Evaluate once · open loop

The parametric example: the graph runs once and builds a result. Source functions are known in advance. The executor evaluates them, runs the solver, then reads the probes, so the graph stays a plain dependency graph. For linear structures it solves once per unit load and scales by f(t) (superposition), so playback is instant.

Simulate · closed loop

The mass-spring, cart-pole and runner examples: a probe feeds back into a source, for example angle → LQR → motor. The executor steps the solver and the flow together on a fixed time step. Validation will reject only loops that have no delay or stateful block in them (algebraic loops); today every cycle in the graph is rejected.

Flow types

Beyond Signal flow

A backend declares which flow types it supports, and a toolkit can require one (an electrical toolkit needs Model flow). Each has its own executor and look. A flow is drawn on sheets. Signal blocks (the base, signal and math packages) work in every type: in a Step flow they run once per clock step and feed conditions and monitors.

Flow typeWires meanLikeState

Model flow · acausal solver

OpenModelica as the Model flow solver

A Model flow is a physical network: wires are connections where effort (voltage, force, pressure) is equal and flow (current, force, mass flow) sums to zero. Solving one means building a DAE, reducing its index and integrating it: years of work to do well. OpenModelica's compiler, omc, already does all of it, with the Modelica Standard Library (MSL) for components. Paperboat uses it as the solver instead of writing one.

StepWhat happensWhere
1 · GenerateThe Model flow sheet becomes Modelica source: each block is an MSL component (Resistor, Mass, Spring, HeatCapacitor), each wire a connect(), each param a parameter. Physical port types (electrical pin, flange, heat port) come from the descriptor, and connection rules (#4) keep wires between matching ones.Engine, from the toolkit's model packages
2 · Compileomc flattens, reduces the index and compiles the model to an FMU (FMI 2/3, co-simulation, its solver inside). Cached by a hash of the generated source.omc as a child process
3 · RunThe engine loads the FMU and steps it on the run clock, alongside the station plant and any Signal or Step flow: probes read FMU outputs, sources set FMU inputs, monitors stream signal events as today.Engine (FMI runtime, e.g. FMI Library)
4 · IterateChanging a param sets an FMU parameter: no recompile. Changing the sheet (a block, a wire) recompiles, which takes seconds; the UI shows it as a compile step with progress.Engine, UI
  • Why an FMU, not omc simulating directly: the engine keeps control of the clock, so a Model flow can close loops with Signal flow blocks and the station, stream live and be cancelled like any run.
  • Toolkit side: a model package (electrical, mechanics, thermal) is a set of templates that map to MSL classes; its blocks declare the Model flow type, so the palette only offers them on a Model flow sheet.
  • Dependency: omc is large (hundreds of MB) and stays an external install the engine finds on the path, not bundled at first. Runtime FMUs are small and self-contained.
  • Licences to check before shipping: OpenModelica (OSMC-PL, with a GPL v3 option) as a separate tool; MSL is BSD-3; generated FMUs are ours.
  • Fallback: our own DAE solver only if FMUs fall short (live structural changes, browser-only runs).
The reusable core

Model → Discretize → Solve → Study

All three domains share this pipeline. The framework owns the stages, caching and execution; each domain plugs in its own blocks for each stage.

ModelThe setup scene, turned into a typed domain model.
DiscretizeMesh, lattice, element assignment, linearization, sample time.
SolveFEA, flow solver, time integration. Often long-running.
StudySweeps, Monte Carlo, limit checks, comparisons, Pareto fronts.
Architecture

Four layers

FrontendStation (three.js), Flow (React Flow), Dashboard (uPlot planned) and Console. Builds every form and block from the backend's catalog, so it has no domain code.
ProtocolOne WebSocket. JSON text messages for the block catalog, the scene, the graph and run events; binary frames for large fields. Language-neutral, so any backend that speaks it works with the UI (see protocol/README.md). Schemas published as JSON Schema.
Core (C++)Toolkit of reusable blocks and TOML descriptors (built) · registry of entity and block types · graph validation and type checking · content-hash cache · thread-pool executor with progress, cancel (std::stop_token) and fan-out · WebSocket server.
Solvers (C++)Solver adapters behind blocks: an Eigen direct-stiffness frame solver, own equations of motion with boost::odeint, a lattice-Boltzmann solver, and later OpenFOAM or CalculiX in podman. Solvers that can't check the stop token run in a child process so cancel always works.
Plugin API

What a domain author writes

A domain is a descriptor plus C++ for what only it can do. The descriptor is a TOML file listing the domain's blocks: templates from the reusable C++ toolkit (waves, math, PID, simulator, keyboard keys, graphs), used as is or renamed and re-defaulted, and the domain's own sources, probes and solver blocks with their ports and params. The engine turns it into the catalog the UI reads, so the frontend has no domain code.

domain = "structural"

[[blocks]]
use = "signal/sine"
defaults = { amplitude = 5000, frequency = 2 }

[[blocks]]
use = "math/threshold"
label = "Limit 10 mm"
defaults = { level = 10 }

[[blocks]]
use = "dashboard/graph"

# The domain's own blocks
[[blocks]]
type = "ForceSource"
kind = "source"
inputs = ["force"]

[[blocks]]
type = "DisplacementProbe"
kind = "probe"
outputs = [{ id = "disp", type = "mm" }]

[[blocks]]
type = "LinearStatic"
kind = "function"
inputs = [{ id = "model", type = "FrameModel" }]
outputs = [{ id = "result", type = "FrameResult" }]
params = { check_tolerance = 1e-6 }

The domain's own blocks are C++ classes bound to their descriptor entries; toolkit entries need no code:

#include <paperboat/plugin.hpp>
using namespace paperboat;

class LinearStatic : public Node {
  Outputs run(Ctx& ctx, const Inputs& in) override {
    ctx.progress(0.1, "assembling stiffness");
    auto result = solve_frame(in.get<FrameModel>("model"), params(), ctx.stop_token());
    ctx.metric("max_displacement_mm", result.max_disp * 1e3);
    return {{"result", std::move(result)}};
  }
};

void register_structural(Domain& d) {
  d.load_descriptor("examples/backends/structural-cpp/descriptor.toml");
  d.implement<LinearStatic>("LinearStatic");
  d.implement<ForceSource>("ForceSource");
  d.implement<DisplacementProbe>("DisplacementProbe");
}
  • Placing a ForceSource or DisplacementProbe on a joint in the station adds a matching block to the flow palette, named after the entity (F1, P1).
  • ctx.progress, ctx.metric, ctx.log and ctx.frame become events on the Dashboard and Console.
  • ctx.stop_token() is a std::stop_token. Solvers check it between iterations; anything that can't runs in a child process that the engine kills on cancel.
  • A block's output is cached by a hash of its inputs and params, so editing one block re-runs only what depends on it.
  • Domains are separate CMake targets: paperboat_structural, paperboat_control, paperboat_cfd. They link statically at first; loadable shared libraries behind a C ABI come later.
  • The toolkit (engine/toolkit) is built and tested: packages base, the simple things meant for every flow type (constant, gain, sum, threshold, saturation, sine, step, ramp, square, key, graph), and control, dynamics on a clock (PID, integrator, lag, plus rk4_step for plants). A descriptor's config fixes load-time settings, so one template can appear twice, e.g. Key ← and Key →.
  • Station entities (Joint, Member) get a descriptor section of their own later; Lua scripting can be added for expression blocks without changing the format.
  • Block definitions are data once they leave the engine, so a domain can also be prototyped in any language that speaks the protocol (examples/backends/) before it is ported to C++.

Libraries

  • Engine: C++20, CMake with presets; dependencies through FetchContent today (vcpkg manifest still an option, decide before CI). nlohmann/json, toml++ for descriptors, Catch2 for tests. Planned: uWebSockets or Boost.Beast for the core server (the C++ example uses IXWebSocket), Eigen, boost::odeint; clang-format and clang-tidy.

Milestones

Order of work

Each milestone ends with something runnable. The core API is allowed to change until M3; after that it is frozen for the first release.

M0 · Skeleton · done

Core with no UI

Done when: a graph loaded from JSON validates in the C++ engine, runs with caching and cancellation, and serves protocol events. Catch2 tests cover type checking, cache hits and cancel. So far: the toolkit, TOML descriptors and engine/core (validation, Signal flow runs with cancellation, the protocol over WebSocket, node events: node.state, node.progress) are done and tested, with a golden cart-pole run. Caching is in: a session keeps each block's last result, and a run that evaluates once reuses the outputs of every pure block (one that declares cacheable, or is stateless) whose type, params, text, wired input values, the variables it read and its files are unchanged, so a changed param, wire, variable or station object recomputes only the blocks it reaches. Runs on a clock, Step flows and blocks that read keys or draw at random always compute; a cancelled run never keeps a block it cut short. Catch2 tests cover hits, invalidation, opt-outs and cancel. Later: a cached node.state (a reused block reports done for now) and caching for runs on a clock.

M1 · Flow page · partly done

Flow and Dashboard

Done when: the web app lists block types from the backend, builds a flow, edits params through generated forms, runs it and shows progress and logs live. Scope, Lamp and Readout instruments work, and dragging a port onto a scope adds a tap. So far: the palette, typed wiring, delete, number params, live plots, progress and Console work against the example backends; the Scope, Graph, Display (a readout), Switch and Lamp instruments and taps are done.

M2 · Structural

Station in 3D

Done when: you can draw a truss bridge in 3D, put a force source on one joint and a probe at midspan, drive the source with a 5 kN sine, graph force against displacement, and see a lamp trip above 10 mm. Saved as examples/truss-bridge.

M3 · Control · partly done

Closed loop, live streaming and fan-out

Done when: the LQR block closes the loop from the angle probes to the motor source with fixed-step execution, and a sweep of 10 Q weights runs in parallel, each case animates live, and a Pareto plot compares settling time against peak force. The double pendulum swaps in with no framework change. So far: the examples close a PID loop (cart-pole) and an LQR loop (double pendulum) on the same framework; the parallel sweep and the Pareto plot are open.

M4 · CFD

Long jobs

Done when: flow past a cylinder shows live vortex shedding and a residual curve, cancels cleanly mid-run, and a Reynolds sweep reports drag. Optional: the same graph runs on OpenFOAM in podman.

Done when: the Electron app installs from an AppImage, MSI or DMG and starts its bundled engine on a clean machine, paperboat-engine serve plus the static web build works in a browser, and the docs include a "write your own domain" tutorial.

Risks

Open questions

  • 3D editor scope. A full CAD tool is out of reach. Start with grid snapping, point and link entities, and a property panel, and add import (STEP, STL) later.
  • Sweep semantics. Grasshopper data trees are powerful but confusing. Start with plain list fan-out (one run per item) and a Collect block.
  • Station ↔ flow link. When the station changes, which blocks are stale? Hash the station per entity so only the affected model blocks invalidate. For a run that evaluates once this holds: the cache compares the values a block gets on its wires, so a changed station object invalidates only the blocks its linked block feeds.
  • Clock alignment. Probes from different solvers sample at different rates. Graphs resample onto the run clock, and diff mode needs matching units (otherwise it falls back to two axes).
  • Probe placement on meshes. A probe at a point that isn't a mesh node has to interpolate. Snap probes to joints first and allow free points later.
  • Large results. CFD fields don't belong in JSON. Send them as compressed binary frames and keep full results on disk with a reference in the cache.
  • C++ builds on three OSes. Pin dependencies with a vcpkg manifest and run CI on Linux, Windows and macOS from M0, not at release.
  • Protocol drift. The C++ engine and the example backends must stay in sync. Generate the TypeScript types and C++ structs from one JSON Schema; every backend already runs the same smoke test.
  • Flow type scope. Model flow and Modes are each a project of their own. Make Signal and Step flow solid first; treat Model flow as an adapter to OpenModelica (generate Modelica, compile to an FMU, step it) before writing a DAE solver.
  • Name. Settled: product Paperboat, handle paperboatlab (GitHub org, domain, package scope).
